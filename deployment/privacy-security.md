# Privacy and security operations

- Analytics preference is `devsprendimai.cookie-consent.v2` in localStorage, mirrored to the non-identifying `devsprendimai_analytics_consent` first-party cookie. It is deliberately exempt from cookie encryption: it grants no account access. Version 2 asks returning visitors again because the notice now explicitly covers internal visitor statistics as well as GA4.
- No consent means no GA tag and no application visitor records. Essential sessions, CSRF, anti-spam rate limits and hosting security logs remain separate. Internal statistics begin with the first page request carrying a granted preference, so they will differ from GA's initial opt-in page view.
- Visitor pseudonyms rotate monthly; raw IP/user-agent values are not stored in visit records. Do not put names, emails or other personal data in UTM campaign parameters.
- `MaintainPrivacyRetention` runs the retention check after a production GET response. A cache lock prevents concurrent passes; a successful pass is cached for 24 hours. At most 1,000 records per table are deleted per pass. Backlogs retry after 10 minutes. Errors are reported and do not break the visitor response. This requires a persistent cache store supporting locks (Laravel database/file/Redis stores).
- Visits older than 90 days and website enquiries older than 2 years are eligible. Existing daily scheduler jobs in `routes/console.php` remain an alternative when hosting cron is available. With request-triggered cleanup, an idle site performs its next check when a visitor returns; there is no publicly accessible cleanup endpoint.
- Back up the database privately before deploying the first retention pass. Keep operational backups access-controlled and rotate them; the application does not prune hosting backups, email correspondence, contracts or accounting records.
- Production must have `APP_DEBUG=false`, HTTPS, `SESSION_SECURE_COOKIE=true`, a persistent non-array cache, and private access to application source and secrets. The middleware adds a deliberately limited CSP, HSTS on HTTPS, browser capability restrictions and no-store for private pages. This does not replace dependency patching, server hardening, access review or incident response.
- Contact forms permit up to 5 submissions/10 minutes and 20/hour per IP-derived cache identifier. Honeypot submissions are silently ignored; all real submissions are length-limited. No captcha or advertising tracker is added.
- Verify cookie refusal, acceptance, withdrawal, LT/EN forms, private-page no-store headers and public pages after deployment. The legal text describes implemented behavior, not a certification of legal compliance; keep controller, provider contracts, accounting/tax status and retention practices reviewed by the owner.

## Release security checks on 15 October 2026

- PHP production dependency audit reports no known advisories after locked compatible security updates. Browser-bundled Vue/Axios dependencies were patched as well.
- The full npm audit still lists 7 transitive build-tool advisories (braces/glob/selector-parser through Tailwind 3). They process trusted repository source during local builds and are not shipped as server-side Node services. Do not run the dev server on a public interface or compile untrusted templates; resolve the remaining toolchain warnings through a separately tested Tailwind migration, not an unreviewed force upgrade.
- Manrope is self-hosted under the bundled assets with its SIL Open Font License; visitors no longer request a third-party font stylesheet.
- Client website credentials are encrypted at rest and hidden from shared/list/edit props. The dedicated detail view requires a recently confirmed administrator password. Private Inertia history is encrypted and logout invalidates its key. Never rotate APP_KEY without an encrypted-data migration/old-key strategy.
- Migration `2026_10_15_000001_encrypt_client_credentials` does not decrypt secrets on rollback. Keep the encrypted model cast when rolling application code back, or restore the matching protected database backup during a controlled rollback. Backups contain personal data and must remain outside the document root.
- At the initial audit, production used `MAIL_MAILER=log` with no SMTP credentials: enquiries were saved in the dashboard but notification/password-reset emails were not delivered. The dashboard warns for log/array mail transports. After configuring the owner's verified provider, refresh the config cache and verify application-level sending, not just SMTP login. Never paste a mailbox password into chat or commit it.
- To configure or rotate the Hostinger mailbox password, run `bash deployment/setup-hostinger-mail.sh` from an interactive SSH shell in the app root. It hides terminal input, uses `smtp.hostinger.com:465` with `MAIL_SCHEME=smtps`, and tests TLS authentication before changing settings. It clears overriding `MAIL_URL`, preserves unrelated settings, creates a private configuration backup outside the document root, refreshes the config cache, verifies Laravel can construct the SMTP mailer, and rolls back configuration on a setup error. No password is accepted in command arguments or printed, and no test email is sent automatically. The SMTP login check is not proof of delivery to the inbox; verify that separately after setup. Provider settings: https://www.hostinger.com/support/1575756-how-to-get-email-account-configuration-details-for-hostinger-email/
- A cleared SMTP URL must resolve to `null`, not an empty string: Laravel's mail manager treats a present URL as a transport override. The mail configuration normalizes empty values, and the setup helper writes `MAIL_URL="null"`. Keep the runtime mailer-construction regression tests when upgrading Laravel/Symfony.
